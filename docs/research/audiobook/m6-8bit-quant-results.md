# M6: 8-bit quantization of Higgs TTS 3 4B (Refs #57)

## Why

The full-precision model occupies roughly 11 GB on a 16 GB machine. Three long chapter runs
were lost on the same day to macOS service scanners (CleanMyMac, Spotlight, MediaAnalysis,
FileProvider) pushing the model into swap mid-run — it stops computing (0% CPU, "sleeping"),
swap fills toward the ceiling, and load average was seen as high as 257 with an idle CPU.
This is not fixed by scheduling those scanners around the run.

The owner's instruction: build an 8-bit quantized checkpoint as an **additional**, opt-in
option — check how much quality is actually lost — while the full-precision model stays the
default.

## What broke with the plain converter, and why

`python -m mlx_audio.convert --hf-path bosonai/higgs-tts-3-4b --mlx-path <out> --quantize
--q-bits 8 --q-mode affine --model-domain tts` runs and produces a checkpoint, but it does
not load:

```
FileNotFoundError: No safetensors with codec prefix
'tied.embedding.modality_embeddings.0.model.' found
```//(`mlx_audio/codec/models/higgs_audio/higgs_audio.py:285`, `from_higgs_tts_checkpoint`)

**Root cause.** Higgs TTS 3's checkpoint bundles two things in one safetensors shard: the
language backbone, and the audio codec (the part that turns discrete codes into a waveform),
stored under the key prefix `tied.embedding.modality_embeddings.0.model.*`. The codec is
loaded independently and later, by `HiggsAudioTokenizer.from_higgs_tts_checkpoint`, which
reads that prefix directly out of whatever safetensors file the TTS checkpoint directory
holds. `mlx_audio.convert`'s TTS `Model` class only recognizes language-backbone tensors in
its own parameter tree; codec tensors under that prefix are not part of it, so `save_model`
(which serializes `model.parameters()`) silently drops all of them. Measured on the original
checkpoint: **927 tensors, 528 of them (57%) under the codec prefix** — and the broken
converted checkpoint had **905 tensors, 0 of them under the codec prefix**.

## Correct approach: quantize the language part, leave the codec alone

This is not a workaround, it's the right call on the merits, and it costs almost nothing in
size:

- **Measured fraction:** the codec is **0.403 GB of 9.310 GB (4.3%)** of the original
  checkpoint's tensor bytes. Quantizing it would risk audio quality for essentially no size
  win, while it's the exact component responsible for turning codes into a waveform —
  precision loss there is much more directly audible than in the language backbone.

**Method used** (`scripts/quantize_higgs_tts.py`): run the standard `mlx_audio.convert`
`--quantize` pass to produce the quantized language-backbone checkpoint (905 tensors, as
above), then copy the 528 codec tensors from the original checkpoint's safetensors file
verbatim (original dtype, no requantization) into the converted checkpoint's
`model.safetensors`, and add their keys to `model.safetensors.index.json`. This works because
the codec loader reads by key prefix directly from the checkpoint directory's safetensors
file(s) — it doesn't care whether the rest of the file also holds a quantized language model.

```
python3 scripts/quantize_higgs_tts.py \
    --hf-path bosonai/higgs-tts-3-4b \
    --mlx-path models/higgs-tts-3-4b-8bit \
    --q-bits 8 --q-mode affine
```

(Or, since the broken checkpoint from the plain converter already exists, `--skip-convert`
just runs the codec merge step against an already-converted directory — this is what was
actually run here, reusing the earlier `mlx_audio.convert` output.)

**Verification — the only one that counts:**

```python
from mlx_audio.tts.utils import load
load("models/higgs-tts-3-4b-8bit", model_type="higgs_audio_v3")  # succeeds
```

Confirmed: the merged checkpoint loads cleanly.

`models/` is local-only (added to `.gitignore`); the quantized checkpoint is not committed,
same as every other model weight in this project.

## `--model` in `src/audiobook.py`

Added `--model` (default: `MODEL_ID = "bosonai/higgs-tts-3-4b"`, unchanged), accepting either
an HF repo id or a local checkpoint directory (e.g. `models/higgs-tts-3-4b-8bit`). Threaded
through the three places that used the hardcoded `MODEL_ID` before: the manifest header
(`build_manifest`), the resume mismatch check (`load_or_create_manifest`), and the model load
call in `main()`.

**Resume safety.** `manifest["model"]` is compared to the current `--model` value as a plain
string on every resume, exactly like `voice_reference` and `fades_ms` already are (same
class of bug: splicing segments generated by two different models/voices/fade settings into
one chapter). This works identically for an HF repo id and a local path — a manifest built
with `bosonai/higgs-tts-3-4b` refuses to resume under `models/higgs-tts-3-4b-8bit`, and vice
versa. Verified both directions with a manual repro and with new tests
(`TestModelSelectionManifestInvalidation` in `tests/test_audiobook.py`):
`test_switching_to_local_quantized_checkpoint_refuses_to_resume`,
`test_switching_from_local_quantized_checkpoint_also_refuses`.

## Measurement setup

Same text (`samples/tts_ru.txt`, 9 Russian sentences, 285 chars, one chunk under the default
`--max-chars 500`), same voice reference (`--voice-name vedmalex_short`), one run each,
through `scripts/run_one_inference.sh` wrapped in `/usr/bin/time -l`, sequentially (never two
inference processes at once, per project policy). `mx.eval()` boundaries are already built
into `audiobook.py`'s per-segment memory capture (`_capture_memory_metrics`), so no
additional flushing was needed for `peak_mlx`.

Commands:
```
scripts/run_one_inference.sh logs/m6_full_run.log /usr/bin/time -l python3 src/audiobook.py \
  --text-file samples/tts_ru.txt --output-dir output/m6_quant_bench/full \
  --voice-name vedmalex_short --assemble --model bosonai/higgs-tts-3-4b

scripts/run_one_inference.sh logs/m6_8bit_run.log /usr/bin/time -l python3 src/audiobook.py \
  --text-file samples/tts_ru.txt --output-dir output/m6_quant_bench/8bit \
  --voice-name vedmalex_short --assemble --model models/higgs-tts-3-4b-8bit
```

**N=1 per model** (one run, one segment each) — a budget/scope limitation, not a claim of
statistical significance. Numbers below are single-run measurements.

## Results — memory (the main number for this task)

| metric | full (bosonai/higgs-tts-3-4b) | 8-bit (models/higgs-tts-3-4b-8bit) |
|---|---|---|
| `weights_on_disk` | 8.7 GB (`model.safetensors` blob) | 4.4 GB (`model.safetensors`, codec merged in) |
| `peak_mlx` (`mx.get_peak_memory()`, in-manifest) | 11,846,566,576 B ≈ **11.03 GB** | 7,838,596,184 B ≈ **7.30 GB** |
| `peak_footprint` (`/usr/bin/time -l`, "peak memory footprint") | 12,627,824,896 B ≈ **11.76 GB** | 12,025,296,064 B ≈ **11.20 GB** |
| (`ru_maxrss`/"maximum resident set size" — NOT cited as a real number, known to undercount on macOS) | 4,848,517,120 B | 5,642,141,696 B |

**Read this carefully — it is not the clean win the owner was hoping for.** `weights_on_disk`
halved as expected, and `peak_mlx` (the number MLX itself reports for arrays it actually
allocated) dropped by ~34% (11.03 → 7.30 GB). But `peak_footprint` — the actual OS-level
process memory high-water mark, which is what determines whether the machine starts
swapping — barely moved: **11.76 GB → 11.20 GB, a ~5% reduction**, nowhere near "~6 GB
instead of ~11 GB." The `ru_maxrss` numbers move in the *opposite* direction (4.85 → 5.64 GB)
and would have been actively misleading if used as "the" number — this is exactly why the
task required citing `peak_footprint`, not `ru_maxrss`.

**What this means for the actual goal (stop the swap-triggered stalls):** on this one
measurement, the 8-bit checkpoint does *not* deliver the OS-level memory headroom the owner
was hoping for. It is real work with a real (if modest) win on `peak_footprint`, a bigger win
on `peak_mlx`, and a real win on `weights_on_disk` and speed (below) — but it should not be
sold as "the swap problem is solved." This is worth a second, longer-chapter measurement
before relying on it operationally; a single 24-second clip may not reflect footprint
behavior over a multi-hour chapter run (e.g. MLX's cache-memory retention behavior, which
also looked non-monotonic here: `cache_memory_bytes` was *higher* for the 8-bit run, 6.44 GB
vs 3.24 GB for full, in the per-segment memory field).

## Results — RTF (speed)

| | full | 8-bit |
|---|---|---|
| `generation_seconds` | 89.42 | 56.18 |
| `audio_duration_seconds` | 23.68 | 21.64 |
| RTF (seconds compute / second audio) | 3.78 | 2.60 |

The 8-bit checkpoint is genuinely faster: RTF 2.60 vs 3.78, about **1.45x**. This is the
clean, unambiguous win of this change.

## Results — objective quality proxies (`m4_prosody_metrics.py`)

**Calibration caveat, repeated from that script's own docstring:** this is a homemade,
uncalibrated estimator (autocorrelation F0, energy-threshold pause detection, band-ratio
spectral proxies) with nothing to check it against. Good for *relative, within-project*
comparison between these two clips, not for exact physical values.

| metric | full | 8-bit |
|---|---|---|
| `duration_s` | 23.68 | 21.64 |
| `f0_median_hz` | 125.0 | 132.6 |
| `f0_std_hz` | 55.7 | 68.2 |
| `voiced_frame_ratio` | 0.660 | 0.708 |
| `num_pauses` / `mean_pause_ms` | 14 / 384.3 | 14 / 337.1 |
| `reverb_tail_ms` | 55.4 | 66.2 |
| `spectral_centroid_hz` | 2461.5 | 2119.2 |
| `spectral_tilt_db_per_khz` | -3.95 | -5.00 |
| `sibilance_ratio` (5-8 kHz) | 0.1162 | 0.0824 |
| `low_band_ratio` | 0.3676 | 0.3731 |

Two things stand out, both consistent with the owner's stated expectation ("на восьми битах
обычно первым страдает не тембр, а мелкое — шипящие..."):

- **Sibilance ratio is 29% lower** on the 8-bit clip (0.082 vs 0.116) and **spectral
  centroid is 14% lower** (2119 vs 2462 Hz) — both point the same direction: less high-
  frequency energy, consistent with duller/quieter sibilants.
- **Total duration is 8.6% shorter** (21.64 s vs 23.68 s) for the *same text*. This could be
  a (harmless) pace difference, or it could mean the 8-bit model spoke faster/dropped
  something — the metrics alone cannot tell these apart. **This needs an ear**, and the
  survey below asks about it directly (missing words, swallowed sounds).

F0 median/spread and low-band ratio are close enough between the two that they read as "same
speaker, same reference," not a voice-identity problem.

## What still needs the owner's ear (I cannot hear the audio)

A task set, `src/sentiment_survey/task_sets/quant_8bit_vs_full.json`, is ready under
`make sentiment-survey`. It asks, blind:

1. Whole-chapter A/B: which one is the full model? (has a `correct_answer` — a real "can you
   tell" test, not just a preference poll)
2. Whole-chapter quality rating for each model separately (naturalness, stray sounds).
3. First-sentence-only A/B — targets the "swallowed first letter" failure mode found by ear
   in an earlier run of this project (not by any metric).
4. Last-sentence-only A/B (`"Радха-Раман."` — short, sibilant-bearing) — targets the sibilance/
   spectral-centroid gap measured above.
5. A stray-sounds question across the whole set — targets the "model composed background
   music" failure mode also found by ear in an earlier run, never by a metric.

Followed the two schema rules that have caused rework twice before in this project:
`hidden.correct_answer` is a clip role (`"A"`/`"B"`), never display text, and every
`answer_kind: "which"` task has at least two clips. Verified with the project's own tests:
`TestCorrectAnswerIsARoleForWhichTasks::test_every_which_task_expects_a_real_role` and
`TestWhichKindNeedsSomethingToChooseBetween::test_no_which_task_offers_fewer_than_two_clips`
both pass against this new file.

## Direct answer to "насколько хуже получается?"

- **Disk footprint:** genuinely, measurably smaller (8.7 GB → 4.4 GB weights on disk).
- **Speed:** genuinely, measurably faster (RTF 3.78 → 2.60, ~1.45x).
- **`peak_mlx` (MLX's own accounting):** genuinely, measurably smaller (11.03 GB → 7.30 GB,
  ~34% less).
- **`peak_footprint` (the number that predicts swap trouble):** only marginally smaller
  (11.76 GB → 11.20 GB, ~5%) on this one measurement — **not** the "problem solved" result
  the owner was hoping for; needs a longer, real-chapter-length re-measurement before being
  trusted operationally.
- **Objective acoustic proxies:** a real, measurable drop in high-frequency content
  (sibilance ratio, spectral centroid) — consistent with quantization dulling exactly the
  "small stuff" (sibilants, breath sounds, word endings) the owner predicted, not the overall
  timbre. A duration difference (-8.6%) that the metrics cannot explain and needs a listen.
- **What I cannot answer:** whether that measured sibilance/centroid drop, or the duration
  gap, is actually *audible* and *bothersome* — that is exactly what the blind survey above
  is for. Based on the numbers alone, my best guess is that this checkpoint is usable for
  drafts and probably fine for many segments, but is not yet demonstrated safe as a
  chapter-wide default until the owner confirms by ear that words aren't being dropped and
  sibilants aren't audibly degraded — and until the `peak_footprint` question above is
  re-checked on a longer run.
