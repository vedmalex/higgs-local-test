# E1: does the DSL reproduce Э0's segment hashes? (issue #114)

Stage E1's stated readiness criterion: "the Э0 chapter reproduces from `.abs` with
identical hashes for unchanged segments." Measured, honest answer: **no, not fully.**
26 of the Э0 manifest's 70 segment hashes reproduce exactly; 44 do not. This is a
structural mismatch between two fixed, unchangeable pieces, not a bug in the compiler
(`scripts/audiobook_dsl.py`) — full root cause below.

## Reproduction

```
samples/audiobook/prepared/chapter-e0-narration.abs   # generated by make_e0_abs.py,
                                                       # one #prose block per source
                                                       # paragraph, no speaker/attrs --
                                                       # matches how Э0 was actually run
output/chapter-114-e0/manifest.json                   # Э0's own manifest (70 segments,
                                                       # local artifact, not committed)
```

```python
doc, segs = audiobook_dsl.compile_source(abs_text)
lines = audiobook.parse_screenplay([{"speaker": s["speaker"], "text": s["text"]} for s in segs])
chunks = audiobook.chunk_screenplay(lines, max_chars=500, tag_scope="sentence")
dsl_hashes = {audiobook._text_hash(audiobook._segment_hash_input(c)) for c in chunks}
manifest_hashes = {s["text_hash"] for s in manifest["segments"]}
len(dsl_hashes & manifest_hashes)  # == 26, not 70
```

`tests/test_dsl.py::TestE0HashReproduction` pins this exact number (26) as a regression
guard, and separately confirms the canonical/coverage checks both pass for this fixture
(so the mismatch is not a compiler or authoring bug — the DSL faithfully reproduces the
source text and every word is covered; it is specifically about *chunk boundaries*).

## Root cause

Э0 was generated the way `src/audiobook.py --text-file` works: the **entire** chapter's
text is split into sentences once (`split_sentences`) and packed into chunks once
(`chunk_sentences`), with no awareness of the source's paragraph breaks. A chunk is only
as long as `max_chars` allows, and the packer is free to start a chunk with the tail
sentence(s) of one paragraph and finish it with the lead sentence(s) of the next. Direct
measurement (locating each of the 70 manifest chunks' first/last sentence back in the
source text and mapping them to paragraph indices) found **16 of 70 chunks span two
different source paragraphs.**

The DSL's grammar closes a block on a blank line (`.claude/skills/audiobook-markup/
references/dsl-spec.md` sec. 2.1) — a fixed rule, needed so `#note`/the next block's
header can never be mistaken for body text. A chapter whose paragraphs are separated by
blank lines (as this one, and as `samples/audiobook/prepare.py`'s output generally is)
therefore compiles to **one screenplay JSON line per paragraph**, not one line for the
whole chapter.

`chunk_screenplay` (`src/audiobook.py`, unmodified, and *by design* — see its own
docstring: "Each screenplay LINE is chunked independently... active state is reset to
none at the start of every line") runs `split_sentences`/`chunk_sentences` separately per
JSON line and never merges two lines' sentences into one chunk, even when both are far
under `max_chars`. This is deliberate on the engine's side (a per-speaker reset needs a
hard line boundary somewhere), but it means the DSL's per-paragraph JSON lines can never
reproduce a chunk that used to span two paragraphs.

The measured overlap (26/70) is lower than a naive "70 − 16 crossing chunks = 54 should
still match" estimate because a merge point shifts every following sentence-grouping
*within that paragraph* (chunk boundaries downstream of a divergence point move too, not
just the merged pair itself), and because two adjacent crossings compound.

## Why this was not "fixed" by changing the DSL or the compiler

Both pieces that create the conflict are outside this stage's mandate to change:

- **The engine (`src/audiobook.py`) is explicitly out of scope for E1** — this project's
  brief for this stage was "the engine does not change at all," and `chunk_screenplay`'s
  per-line independence is a documented, deliberate design choice there (state reset at
  a speaker boundary), not an oversight.
- **The DSL's blank-line-closes-block rule is the format's basic structural anchor** —
  there is no other syntax in this spec for "these two blocks are actually one" (and
  inventing one, e.g. a block-continuation marker, would need the project owner's
  sign-off, since it changes the format after this same round already deliberately
  *removed* two block types to keep the grammar small — see dsl-spec.md sec. 6).

## What this means in practice

- For a **chapter never generated before**, this mismatch is irrelevant — there is no
  prior audio to preserve, and the DSL-driven chunk boundaries are just as valid as
  Э0's continuous-stream ones (neither is "more correct"; they're different, equally
  legitimate packings of the same sentences under the same `max_chars` budget).
- For **migrating an already-generated chapter (like Э0) onto DSL authoring**, only
  26/70 = 37% of existing segment audio would be reused; the other 63% would regenerate
  even though the underlying words did not change. This is a real cost that should be
  weighed before migrating any already-narrated chapter to `.abs`, and is worth raising
  with the project owner explicitly rather than assumed away.

## Open follow-up (not resolved here)

Whether a future DSL revision should add an explicit block-continuation marker (so an
author can say "this `#prose` block is the same speech as the previous one, don't reset
chunk packing at this boundary") is a real design question, but out of scope for E1 and
requires an owner decision given the format was just deliberately trimmed down.
