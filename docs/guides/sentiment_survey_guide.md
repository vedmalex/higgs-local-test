# Слепая проверка тегов/сентимента — руководство (Refs #57)

Локальное приложение для честной слепой проверки, которую требует гейт сентимента в
`docs/research/audiobook/m4-plan.md` (§2, §3, M4-T4): не менее 8 слепых пар, вердикт выносит
владелец, провал если он различает варианты в пользу неквантованного более чем в 6 случаях из 8.
Раньше владелец слушал файлы в файловом менеджере и видел их имена — слепота терялась.

## Запуск

```bash
make sentiment-survey
```

Одна команда: стартует локальный HTTP-сервер на `127.0.0.1:8877` (стандартная библиотека
Python, без Flask и прочих зависимостей — `.venv-tts`'s Python 3.12 достаточно) и открывает
браузер. Остановить — `Ctrl+C`. Порт можно поменять: `python3 src/sentiment_survey/server.py 9000`.

**Аудио не генерируется.** Приложение только читает уже существующие `.wav` из `output/` —
безопасно запускать, даже если GPU занят другим прогоном.

## Что откроется

Список наборов заданий, отсортированный по приоритету:

1. **`unheard_sfx_env`** — 9 `sfx:*` + 2 `env:*` тегов, которые человек ещё ни разу не слышал
   (issues #116, #119). Автообнаружено сканированием `output/m4_tag_catalog/tag_sfx_*.wav` /
   `tag_env_*.wav`.
2. **`disputed_tags`** — теги из групп B/C объективной триажи M4-T5 (слабый/неоднозначный сигнал
   по F0/темпу/паузам): `arousal`, `confusion`, `helplessness`, `longing`, `expressive_high`,
   `pause`, `singing`, `anger`, `enthusiasm`. Список выводится автоматически из
   `docs/guides/tag_reference.md`, не зашит в код.
3. **`final_intonation`** и **`boundary_check`** — завершающая интонация (метрика зашумлена
   скрипучим голосом нейтральной базы этого прогона — решает только слух) и проверка, не
   переоткрывается ли тег эмоции на границе куска текста.
4. **`stress`** — 22 клипа, 3 пары омографов (замок/стоит/атлас) × до 6 нотаций ударения.
5. Всё остальное: уже частично подтверждённые теги (группа A), второй независимый прогон
   `output/m4_tags/`, первая проверка `output/m4t0_*`, бонусный набор «эмоция против эмоции».

Каждый набор показывает `отвечено / всего`; уже пройденный набор можно открыть заново,
переслушать и при необходимости исправить любой ответ (см. «Навигация и исправление ответа»
ниже — старый ответ при этом не пропадает).

## Как отвечать

- Клипы проигрываются без подписи — только «Клип 1» / «Клип 2» (порядок A/B рандомизируется на
  старте сервера, чтобы не выработалась привычка угадывать по позиции).
- Варианты ответа зависят от типа задания (парное сравнение «отличаются ли?», парное сравнение
  «какой из двух...?», одиночная оценка «слышен ли здесь шёпот?» и т.п.) — тип и текст вопроса
  берутся из набора заданий, не из кода.
- Если у задания уже есть более ранний устный вердикт владельца (докопировано из
  `docs/guides/tag_reference.md` / `m4-sentiment-results.md`), под вопросом появляется пометка, а
  в списке ответов — дополнительная кнопка «Пропустить — уже есть более ранний вердикт». Сам тег
  эта пометка не раскрывает — только то, что по нему уже что-то известно; конкретика открывается
  после ответа (или после пропуска), как обычно.
- После ответа сразу раскрываются скрытые метаданные: какой тег/вариант это был, что показывают
  метрики, совпал ли ответ с ожидаемым результатом.
- Рядом с вариантами ответа — необязательное **поле свободного текста**: см. «Свободная заметка»
  ниже.
- Клавиши: **1–9** — выбрать вариант ответа по номеру, **R** — переслушать первый клип сначала,
  **Enter** — перейти к следующему заданию после раскрытия ответа, **← / →** — предыдущее /
  следующее задание.
- Закрыть вкладку и вернуться позже можно в любой момент — уже отвеченное не переспрашивается
  (пока сервер работает с тем же `output/sentiment_survey_results/`; если сервер перезапущен,
  прогресс всё равно читается заново с диска при каждом старте).

## Пары по высоте голоса (pitch-pairing)

Владелец во время слепой проверки заметил: «в некоторых случаях женский и мужской голоса, можем
ли мы сравнивать однополые голоса?». Замечание верное и серьёзное: Higgs не закрепляет голос
между генерациями (ни seed, ни reference audio не передаются) — медиана основного тона по 70
сегментам одной главы гуляет от 83.9 до 203.4 Гц (mean 135.3, stdev 28.6 Гц), то есть пара
«тег/нейтраль» или «эмоция A/эмоция B» с равной вероятностью может оказаться разнополой. Если
так, разница в звучании пары объясняется в первую очередь регистром голоса, а не действием тега
— и ответ владельца по такой паре ничего не говорит про эмоцию.

Что сделано:

- `src/sentiment_survey/pitch.py` меряет медиану основного тона КАЖДОГО звукового файла во всех
  наборах заданий — переиспользуя уже существующий автокорреляционный измеритель
  `docs/research/audiobook/m4_prosody_metrics.py` (никакого второго измерителя не заведено, как
  и просил владелец).
- Порог «близко по высоте» подобран на данных, не на глаз: метод Отсу (Otsu, 1D, два класса) по
  медианам F0 всех клипов набора заданий находит значение в Гц, которое делит корпус на две
  группы, минимизируя разброс внутри каждой — то же самое, чем обычно разделяют «мужской» и
  «женский» кластеры по высоте голоса, только вычислено по собственным данным проекта, а не
  взято из общих таблиц. При последнем прогоне (81 клип) порог составил **≈172.7 Гц**; конкретное
  число печатается в лог сервера при каждом запуске (`Pitch-pairing threshold: ... Hz`) и
  пересчитывается заново по актуальному набору клипов.
- Два клипа считаются «сравнимыми» только если их медианы F0 лежат по одну сторону от этого
  порога. Задания, где пара не прошла порог, **не удаляются и не скрываются** — они остаются
  видимыми и отвечаемыми, но помечаются `pitch_warning` (видно уже до ответа — это не раскрывает
  тег, только факт несовпадения по высоте) и **не учитываются** в статистике совпадения с
  ожиданием/гейта различения в `/api/sets/<id>/summary` и `answers.md` (отдельный счётчик
  `pitch_unreliable_total` / «Недостоверно по высоте голоса»). Ответ на такое задание всё равно
  сохраняется — честность важнее чистоты цифр.
- На реальных данных этого прогона проверка сразу же показала масштаб проблемы: 7 из 10 пар в
  наборе «эмоция против эмоции» (в т.ч. sadness/elation — 108 Гц против 214 Гц, почти октава)
  оказались разнополыми. Это значит, что часть прежних выводов по парам «эмоция против эмоции»
  могла быть подтверждена искажённо — регистром голоса, а не тегом эмоции. Пары тег/нейтраль в
  пределах одного каталога затронуты меньше (~28%), но тоже не нулём.
- Если numpy недоступен в интерпретаторе, которым запущен сервер (например, голый `python3` без
  `.venv-tts`), анализ высоты тона просто пропускается с предупреждением в лог — приложение
  по-прежнему работает на голой стандартной библиотеке, эта возможность используется, только
  когда доступна (`make sentiment-survey` предпочитает `.venv-tts`, где numpy уже есть).

## Формулировка вопроса «отличаются ли клипы»

Владелец также отметил: «не совсем понятно что значит звучат ли они одинаково, голоса, я так
понял совсем разные — они похоже не будут звучать же». Он прав, и это была наша формулировка —
старый вопрос («Отличаются ли эти два клипа по звучанию (интонация, **тон голоса**, манера)?» с
вариантом «Нет, **звучат одинаково**») звучал как вопрос про тождество голоса, а голоса и правда
всегда разные (см. «Пары по высоте голоса» выше) — отвечать на такой вопрос слухом бессмысленно,
ответ уже известен из измерений. Вопрос переформулирован (`catalog.DIFFER_QUESTION`): теперь он
явно спрашивает только про **подачу** речи (интонация, эмоциональная окраска, темп) и прямо
говорит, что сами голоса могут отличаться и это не проверяется на слух. Слух остаётся там, где
числа не помогают — эмоция, паузы, ударения, естественность произношения; вопрос про тождество
голоса из опросника убран.

## Навигация и исправление ответа

Раньше единственный способ двигаться по заданиям был «вперёд по одному», а исправить ошибку —
руками редактировать `answers.jsonl`. Теперь:

- **Список заданий** — слева от текущего задания. Показывает все задания набора по порядку, с
  отметкой (`✓` отвечено, `·` не отвечено, `–` пропущено), и позволяет перейти к любому заданию
  кликом — не только к следующему по очереди. Кнопку можно свернуть («Скрыть»/«Показать»), если
  мешает на маленьком экране.
- **Кнопки «← Назад» / «Вперёд →»** (и клавиши со стрелками) листают задания по порядку набора,
  включая уже отвеченные — так можно перепроверить, что именно было отвечено, не выходя из
  задания в общий список.
- **Возврат к отвеченному заданию** сразу показывает прежний ответ, совпадение с ожидаемым (если
  оно есть) и раскрытые метаданные — по кнопке «Исправить ответ» можно ответить заново.
- **Исправление не переписывает старый ответ.** Новая запись дописывается в `answers.jsonl` как
  отдельная строка с пометкой `is_correction: true`, `revision` (номер попытки по счёту) и
  `replaces_revision` (какую попытку она заменяет по счёту). Прежний ответ остаётся в файле
  навсегда. **Почему так, а не перезаписью:** если человек передумал — это само по себе значимый
  факт (например, метрики спорные, и первый инстинктивный ответ отличается от обдуманного), и
  выбрасывать эту информацию означало бы терять часть результата слепой проверки, а не только
  «поправлять опечатку». При подсчёте итогов (`answers.md`, `/api/sets/<id>/summary`) всегда
  используется **последняя** запись по каждому `task_id` — именно она и есть текущий ответ
  владельца.
- **Честность про слепоту.** После первого ответа метаданные задания раскрываются в интерфейсе —
  значит, второй (и любой следующий) ответ на то же задание уже не слепой: владелец на момент
  ответа знает, что за клип он слушает. Каждая такая запись помечается
  `answered_after_reveal: true`, и подсчёт «слепых» пар/долей совпадения (гейт из `m4-plan.md`)
  такие записи **не учитывает** — они исключены из блока «слепых» результатов и показаны отдельно
  (`answered_after_reveal` в сводке). Решение сознательное: подмешивать неслепой повторный ответ
  в статистику слепой проверки было бы нечестно по отношению к самому гейту, а тихо снова
  «заблиндовать» интерфейс (скрыть уже увиденные метаданные) означало бы обманывать владельца
  насчёт его собственной прошлой сессии — этого приложение не делает.
- Старые файлы `answers.jsonl` (без полей `revision`/`is_correction`/`answered_after_reveal`,
  записанные до этой возможности) читаются как есть — отсутствующие поля трактуются как «не
  исправление, отвечено вслепую», ничего не ломается.

## Свободная заметка

Готовые варианты ответа ловят только то, о чём мы догадались спросить заранее. Свободный текст
ловит остальное — например, находки вроде «шёпот звучит как тихий звук», «голос между
фрагментами разный», «фон гуляет» не укладывались ни в один вариант ответа и раньше терялись бы
в разговоре, а не попадали на диск.

- **Необязательное поле** рядом с вариантами ответа на каждом задании (и в карточке уже
  отвеченного задания). Пустое значение — это нормально, отправке ответа не мешает.
- **Доступно и для уже отвеченного задания.** Вернувшись на задание, владелец видит свою прежнюю
  заметку и может её дописать или изменить кнопкой «Сохранить заметку» — не обязательно менять
  сам вариант ответа.
- **Хранится через тот же механизм ревизий**, что и исправление ответа: правка заметки
  дописывает новую строку в `answers.jsonl` (`revision`, `is_correction`) — второго хранилища для
  заметок нет.
- **Важно: заметка сама по себе не портит слепоту.** `is_correction` и
  `answered_after_reveal` выставляются, только если фактически изменился сам ответ
  (`answer_label`/`answer_role`) относительно предыдущей записи по этому заданию. Если владелец
  просто дописал или отредактировал заметку, не поменяв вариант, — это **не** считается
  исправлением и **не** выкидывает ответ из «слепой» корзины гейта. Логика: слепоту портит
  раскрытие метки в момент принятия решения, а не то, что человек словами описал уже услышанное
  после решения. (Если бы заметка сама по себе метилась как исправление, любое дополнение к уже
  отвеченному заданию тихо уменьшало бы число «слепых» ответов в гейте — совершенно ложный сигнал:
  решение-то не менялось.)
- **Попадает в `answers.md`** — под каждым заданием, где есть заметка, отдельным пунктом
  «Заметка владельца» и цитатой (`>`), чтобы такие находки было легко скопировать в документацию
  или скиллы.
- Старые записи без поля `note` читаются как «заметки нет» (пустая строка), ничего не ломается.

## Текст под эмоцию

Владелец: «текст идет нейтральный и можно различить только нотки в голосе, но помогало бы
разобраться само выражение». Справедливо — на нейтральном тексте эмоция слышна только оттенком.

**Это меняет, что именно измеряется**, и здесь важно не выдавать это за просто «улучшенный»
замер:

- Старый способ (существующие наборы) держит текст **постоянным** (нейтральным) и меняет только
  тег — различие в звучании относится на счёт тега.
- Наивная замена «нейтральный текст» → «текст под эмоцию» при сравнении тег/нейтраль смешала бы
  сразу два фактора (и текст, и тег) — результат стало бы невозможно приписать чему-то одному.
- Вместо этого новый набор (`emotion_matched_text`, `catalog.build_emotion_matched_text_set()`)
  держит текст под эмоцию **постоянным** и меняет только тег (есть/нет) — так же, как старый
  способ, но на другом, не нейтральном тексте. Такой ответ говорит: «добавляет ли тег что-то
  СВЕРХ того, что уже несёт сам текст», а не «слышна ли эмоция вообще». Это ДРУГОЙ вопрос, чем
  старый набор, и цифры этих двух наборов **не заменяют друг друга** — тег может показывать
  сильный эффект на нейтральном тексте и слабый на подходящем (там текст сам уже несёт большую
  часть окраски, тегу меньше что добавлять) — это будет реальным и полезным результатом, а не
  противоречием, которое нужно объяснять.
- Тексты подобраны из `samples/audiobook/prepared/` (Шримад-Бхагаватам) под каждую из 21
  эмоции; там, где подходящей фразы не нашлось, короткая фраза сочинена и явно помечена
  `[СОЧИНЕНО]`. Полный список текстов с источниками —
  `docs/research/audiobook/m4-emotion-matched-texts.md` (по прямой просьбе владельца — тексты
  сохранены для документации/скиллов).
- **Статус: только тексты и код-заготовка, аудио ещё не сгенерировано.** Эта задача выполнялась
  под ограничением «не запускать генерацию» — сама TTS-модель не вызывалась. Набор
  `emotion_matched_text` появится в приложении автоматически (тем же механизмом
  автообнаружения, что и всё остальное), как только кто-то сгенерирует пары клипов
  (тег/без тега на одном и том же тексте под эмоцию) и положит их в
  `output/m4_emotion_matched_text/` с `manifest.json` — формат описан в том же файле.

## Куда пишутся результаты

`output/sentiment_survey_results/<набор>/` (каталог не попадает в Git — `output/` в
`.gitignore`):

- `answers.jsonl` — машиночитаемый, **append-only** (ничего не перезаписывается): один
  JSON-объект на строку — `task_id`, тип задания, текст вопроса, ответ владельца, `listen_ms`
  (сколько слушал), отметка времени, скрытые метаданные, ожидаемый ответ (если есть), совпадение
  с ним, `note` (свободная заметка владельца, может быть пустой строкой), `pitch_warning`
  (не `null`, если пара не прошла порог по высоте голоса — см. «Пары по высоте голоса»), и
  `revision`, `is_correction`, `replaces_revision`, `answered_after_reveal` — см. «Навигация и
  исправление ответа» и «Свободная заметка». Один `task_id` может встретиться несколько раз
  (исправления и/или правки заметки); текущий ответ — последняя строка с этим `task_id`.
- `answers.md` — человекочитаемый отчёт с той же информацией в виде таблицы + список раскрытых
  метаданных по каждому заданию.

Оба файла переписываются **атомарно** (временный файл + `os.replace`) после каждого ответа —
прерванная сессия не портит уже записанные ответы.

## Сводка по набору

По завершении набора показывается: сколько заданий отвечено, сколько пропущено как уже
известное, сколько исправлено уже после раскрытия меток (`answered_after_reveal` — не входит в
статистику ниже), сколько недостоверно по высоте голоса (`pitch_unreliable_total` — см. «Пары
по высоте голоса», тоже не входит в статистику ниже), сколько пар «различил / не различил» (для
гейта из `m4-plan.md` — порог "не более 6 неразличённых из 8"), и по заданиям с известным
правильным ответом (ударения, завершающая интонация, парные "какой из двух...") — доля
совпадений с ожиданием. Все эти цифры считаются по **последнему** ответу на каждое задание.

## Как добавить новый набор заданий

- **Материал уже лежит в `output/m4_tag_catalog/` или `output/m4_tags/`** — ничего добавлять не
  нужно, `src/sentiment_survey/catalog.py` пересканирует каталоги при следующем запуске сервера.
- **Новый прогон в новом каталоге `output/...`** — добавьте функцию-сканер в `catalog.py` по
  образцу существующих (`build_m4t0_set`, `build_boundary_check_set`): никогда не сравнивайте
  клипы из разных прогонов друг с другом, используйте локальную нейтральную базу того же
  прогона/каталога, если она есть.
- **Вопрос сложнее, чем «отличаются ли эти два клипа»** (тройное сравнение с эталоном,
  специфичная формулировка) — добавьте `.json`-файл в `src/sentiment_survey/task_sets/` по
  образцу `stress.json`/`final_intonation.json`; схема описана в комментариях `server.py`
  (`TaskSet._validate`).

## Перенос вердиктов в `tag_reference.md`

Каждая запись в `answers.jsonl` содержит `hidden.A.tag` (или `hidden.A.marker`/`hidden.A.word`
для наборов вне каталога тегов), ответ владельца и совпадение с ожиданием — этого достаточно,
чтобы вручную или скриптом сверить со статусами в `docs/guides/tag_reference.md` §2 и обновить
строки «Статус проверки на слух». Сам перенос это приложение не делает.
