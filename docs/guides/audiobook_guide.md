# Higgs Audio v3: Руководство по созданию многоголосых аудиокниг (Audiobook Production Guide)

Данное руководство описывает рабочий процесс создания аудиокниг: разметку главы в виде DSL (реплики + эмоциональные теги), нарезку и сборку через движок `src/audiobook.py`, вставку пауз и экспорт готовых глав в **Higgs Audio v3**.

> **Статус (2026-08, Refs #57):** формат из раздела 3 теперь реально читается движком
> `src/audiobook.py --screenplay-file ...` — раздел 4 переписан на это; отдельный
> самодостаточный Python-пайплайн, который был здесь раньше, удалён, потому что он не
> проходил через нарезку/переоткрытие тегов/манифест движка (см. раздел 4 ниже, почему
> это важно). Многоголосье (колонка `speaker`) движком **принимается и валидируется, но
> не подключено** — см. раздел 3a.

---

## 1. Архитектура проекта аудиокниги

Для создания аудиокниги организуется следующая структура папок:

```text
higgs-local-test/
├── voices/                     # Библиотека профилей голосов (.npy или .wav)
│   ├── narrator.npy            # Голос рассказчика / диктора
│   ├── narrator.txt            # Текст референса рассказчика
│   ├── character_krishna.npy   # Голос Кришны
│   ├── character_krishna.txt
│   ├── character_arjuna.npy    # Голос Арджуны
│   └── character_arjuna.txt
├── book/                       # Сценарий книги по главам
│   ├── chapter_01.json
│   └── chapter_02.json
└── output/
    └── audiobook/              # Готовые сшитые главы аудиокниги
        ├── chapter_01.wav
        └── chapter_02.wav
```

## 2. Подготовка и сохранение голосов персонажей

Каждый персонаж создаётся из короткого 7–12 секундного образца речи (см. [Voice Cloning Guide](voice_cloning_guide.md)) и один раз сохраняется в папку `voices/`:

```python
import numpy as np
from pathlib import Path
from mlx_audio.tts.utils import load

model = load("bosonai/higgs-tts-3-4b", model_type="higgs_audio_v3")
Path("voices").mkdir(exist_ok=True)

def register_voice(name: str, wav_path: str, ref_text: str):
    codes = model.encode_reference_audio(wav_path)
    np.save(f"voices/{name}.npy", np.array(codes))
    Path(f"voices/{name}.txt").write_text(ref_text, encoding="utf-8")
    print(f"Голос зарегистрирован: voices/{name}.npy")

# Пример регистрации персонажей:
# register_voice("narrator", "samples/narrator_ref.wav", "В тихой заводи реки плещется чистая вода...")
# register_voice("arjuna", "samples/arjuna_ref.wav", "Сегодня мы начинаем новый важный проект...")
```

> **Честно про текущий статус (Refs #57):** этот код регистрации голосов рабочий сам по
> себе (`encode_reference_audio` — часть API модели), но `src/audiobook.py` **ничего из
> `voices/` не читает**. Реальное подключение per-speaker голоса к генерации — отдельная
> задача (см. раздел 3a). Пока что вся книга, независимо от `speaker`, озвучивается одним
> голосом модели по умолчанию.

## 3. Формат разметки главы (Сценарий книги)

Глава книги сохраняется в виде структурированного файла (например, `book/chapter_01.json`), где для каждого абзаца или реплики задаётся персонаж, эмоциональные теги и текст:

```json
[
  {
    "speaker": "narrator",
    "text": "Глава первая. На поле битвы Курукшетра собрались воины двух армий."
  },
  {
    "speaker": "arjuna",
    "text": "<|emotion:sadness|><|prosody:speed_slow|>О Кришна, видя моих родственников, готовых к бою, мои члены слабеют, а в горле пересыхает."
  },
  {
    "speaker": "krishna",
    "text": "<|emotion:contentment|>О Арджуна, откуда пришла к тебе эта скверна в столь критический час? Она не подобает арию и не ведёт в высшие миры."
  },
  {
    "speaker": "narrator",
    "text": "Услышав слова Господа, Арджуна опустил лук и погрузился в глубокие раздумья."
  }
]
```

Обязательные поля каждой реплики — `speaker` (непустая строка) и `text` (непустая строка,
может содержать `<|category:tag|>`-теги в любом месте). Любые другие поля (заметка
редактора, стабильный id, ссылка на страницу источника и т.п.) можно добавлять свободно —
движок их читает, но **игнорирует** при определении того, что изменилось: правка такого
поля никогда не вызовет перегенерацию реплики (см. раздел 4).

### 3a. Многоголосье: что реально работает, а что только принимается

Поле `speaker` **валидируется, нормализуется и прокидывается через весь манифест**
(`src/audiobook.py`'s `parse_screenplay`/`chunk_screenplay`) — так что менять состав
персонажей, переименовывать их и опираться на смену говорящего как на границу нарезки
можно уже сейчас. Но **реального подключения голоса персонажа к генерации нет**:
`generate_segments` вызывает `model.generate(text=...)` без `ref_audio_codes`/`ref_text`,
то есть **каждая реплика, независимо от `speaker`, звучит одним и тем же голосом модели
по умолчанию**. Если в сценарии больше одного уникального `speaker`, движок явно
предупреждает об этом (`UserWarning`, перечисляет всех говорящих) при каждом запуске —
это не тихое ограничение.

Причина, почему это не реализовано сейчас, а не просто "не успели": единственный замер
клонирования голоса в этом проекте показал RTF 7.73 против 6.56 у обычной генерации —
то есть клонирование **медленнее**, а не только "непроверено". Подключать per-speaker
голос в `generate_segments` — отдельная задача с собственным замером качества/скорости,
а не однострочная правка.

## 4. Запуск через движок `src/audiobook.py`

Раньше здесь был отдельный самодостаточный скрипт (один вызов `model.generate()` на
реплику, ручная склейка `np.concatenate`). Он больше не приводится: для реплики длиннее
одного вызова модели он тихо терял эмоциональный тег на второй части текста (доказано
измерением, см. `docs/research/audiobook/m4-chapter-results.md` §2 — тег не переживает
границу независимого вызова модели без явного переоткрытия), не умел возобновляться
после сбоя и не давал переиспользовать уже сгенерированные реплики при точечной правке.
`src/audiobook.py` умеет всё это — сценарий проходит **ту же нарезку на предложения,
чанкинг с переоткрытием тегов на границах, посегментный манифест с возобновлением и
потоковую сборку**, что и обычный текст; отдельного пути генерации для сценария нет.

```bash
# Проверить нарезку без обращения к модели (какие чанки получатся, где переоткрываются
# теги, кто говорит):
.venv-tts/bin/python3 src/audiobook.py \
  --screenplay-file book/chapter_01.json \
  --output-dir output/audiobook/chapter_01 \
  --dry-run

# Сгенерировать все реплики (создаёт/обновляет output/audiobook/chapter_01/manifest.json
# и один WAV на сегмент) и сразу собрать главу:
.venv-tts/bin/python3 src/audiobook.py \
  --screenplay-file book/chapter_01.json \
  --output-dir output/audiobook/chapter_01 \
  --tag-scope sentence \
  --assemble \
  --continue-on-error

# Прервали на середине? Тот же вызов продолжит с непройденных сегментов (манифест
# перечитывается, готовые WAV проверяются на целостность, а не просто "файл существует").
```

**Инкрементальная правка (ключевое свойство, Refs #57):** каждый сегмент сохраняется под
именем `segment_<hash>.wav`, где `<hash>` — это SHA-256 от **говорящего и итогового
текста реплики** (включая переоткрытые теги), а не от всей записи целиком и не от номера
реплики. Значит:

- правка текста ОДНОЙ реплики при повторном запуске перегенерирует ровно её сегмент —
  остальные подхватываются из `manifest.json` по неизменившемуся хешу, даже если реплика
  сдвинулась по номеру из-за вставки/удаления соседних строк;
- правка постороннего поля реплики (заметка, id, что угодно кроме `speaker`/`text`) не
  меняет хеш вообще — `parse_screenplay` отбрасывает такие поля до того, как текст
  доходит до хеширования;
- переименование говорящего у неизменной реплики **меняет** хеш и требует перегенерации —
  это осознанное решение: `speaker` выбирает голос, как только клонирование будет
  подключено (см. 3a), поэтому смена говорящего — это реальное изменение того, что должно
  прозвучать, а не косметика.

Это свойство проверено тестами: `tests/test_audiobook.py`'s
`TestScreenplayIncrementalRegeneration` — сценарий из 4 реплик, правка одной, повторный
запуск перегенерирует ровно один сегмент; отдельный тест подтверждает, что правка
постороннего поля не трогает ни одного сегмента.

### 4a. Батчинг (`--batch-size`, Refs #114)

До этого исправления `generate_segments` вызывал `model.generate()` по одному сегменту за
раз даже несмотря на то, что замер (`docs/research/audiobook/m4-batching-results.md`,
`m4-batching-stage-profile-results.md`) уже показал ускорение 3.40–3.69× у
`model.batch_generate()` при batch=8 без обнаруженного потолка по памяти. Рабочий конвейер
шёл на базовой скорости, а десятичасовая книга считалась бы 40–60 часов вместо
обещанных десяти. Теперь `--batch-size N` (N > 1) группирует ещё не сгенерированные
сегменты по N штук и прогоняет каждую группу через `model.batch_generate()`:

```bash
.venv-tts/bin/python3 src/audiobook.py \
  --screenplay-file book/chapter_01.json \
  --output-dir output/audiobook/chapter_01 \
  --batch-size 4 \
  --assemble \
  --continue-on-error
```

Что сохранено в точности при переходе на батч (детали и тесты —
`tests/test_audiobook.py`'s `TestBatchGenerationIntegration`):

- **Сопоставление сегментов не перепутано.** Результат каждого элемента батча
  сопоставляется со своим сегментом по `BatchGenerationResult.sequence_idx`, а не по
  порядку возврата — та же конвенция, что в `m4_batching_bench.py`.
- **Манифест пишется атомарно после КАЖДОГО сегмента**, даже внутри одного батча, а не
  один раз после всего батча — `model.batch_generate()` и так отдаёт результаты по одному
  по мере готовности, так что убийство процесса в середине батча теряет максимум один
  ещё не досчитанный сегмент, а не весь батч.
- **Проверка вменяемости аудио** (`_validate_generated_audio`) применяется к каждому
  сегменту батча отдельно — один плохой сегмент в батче не портит остальные.
- **Повтор при сбое:** сначала повторяется батч целиком (до `--max-retries` раз) — общий
  проход модели не даёт понять, какая именно строка виновата, пока батч не завершится.
  Если батч продолжает падать на этом размере, оставшиеся (ещё не готовые) сегменты
  делятся пополам и повторяются рекурсивно, в пределе — по одному через обычный
  `model.generate()`. Это одновременно изолирует реально сломанный сегмент и служит
  автоматической деградацией к меньшему батчу при нехватке памяти.
- **`--batch-size 1`** — это в точности прежнее поведение (один `model.generate()` на
  сегмент), сохранённое как отдельный путь в коде, а не как частный случай батча, для
  честного сравнения и отката.

Значение по умолчанию — **4**, не измеренные 8: замер покрывал лишь десятки сегментов, а
глава — это сотни, и потолок по памяти на таком масштабе не проверялся. `--batch-size 8`
воспроизводит именно измеренную конфигурацию, но выбирайте её осознанно на первом прогоне
новой главы. См. `docs/research/audiobook/m4-batching-integration-results.md` за замером
до/после на рабочем конвейере.

## 5. Таблица рекомендуемых пауз в аудиокниге

| Переход | Рекомендуемая пауза | Назначение |
| :--- | :---: | :--- |
| **Между предложениями одного абзаца** | `0.3 – 0.5 сек` | Естественный вдох диктора |
| **Между абзацами** | `0.7 – 1.0 сек` | Смена мысли или сцены |
| **Между репликами разных персонажей** | `0.9 – 1.2 сек` | Обозначение смены говорящего |
| **Перед и после эпиграфов / стихов** | `1.5 – 2.0 сек` | Выделение важного фрагмента |
| **Между главами книги** | `2.5 – 3.5 сек` | Завершение смыслового блока |

Первые две строки — про паузы `assemble_chapter` уже вставляет между всеми сегментами
через `--silence-ms` (по умолчанию 200 мс). Третья строка (смена персонажа) доступна
отдельно через `--speaker-change-silence-ms`: если задан, эта длительность используется
именно на стыке сегментов с разным `speaker`, а `--silence-ms` — на всех остальных
стыках, например:

```bash
.venv-tts/bin/python3 src/audiobook.py \
  --screenplay-file book/chapter_01.json \
  --output-dir output/audiobook/chapter_01 \
  --assemble --silence-ms 400 --speaker-change-silence-ms 1000
```

Автоматической паузы для эпиграфов/стихов или межглавных пауз нет — они, как и раньше,
дело ручной сборки нескольких `chapter.wav` во внешнем шаге (раздел 6), а не поля этого
движка.

## 5a. Что реально проверено в контрольных тегах

Раздел 3 использует теги `<|emotion:...|>`/`<|prosody:...|>`/`<|style:...|>`/`<|sfx:...|>`
из полного набора модели (43 тега: 21 emotion + 10 prosody + 3 style + 9 sfx, см.
`VALID_TAGS` в `src/audiobook.py`). Метриками (F0, паузы, темп) проверены 34 из 43 —
все emotion/prosody/style теги
(`docs/research/audiobook/m4-tag-inventory-results.md`); все 9 `sfx:*` тегов не
проверялись вовсе, ни слухом, ни метриками. Метрика — это не то же самое, что
подтверждение на слух: объективная триада делит проверенные 34 тега на группы A (чёткий,
устойчивый сигнал по метрикам — 15 эмоций плюс несколько `prosody`/`style` тегов), B
(слабый/смешанный сигнал) и C (сигнал близок к нейтральному или противоречит названию
тега). Владелец прослушал вживую только часть материала — см. ниже, что именно.

**Эмоции (группа A) — подтверждены и метриками, и на слух, но с оговоркой.** Владелец
подтвердил парy `sadness`/`elation` отдельно и сильно («грусть действительно грустная»,
`m4-sentiment-results.md` §6), а по итогам полной инвентаризации — более широко и
осторожно: **«эмоции вроде различимы и работают»** (`m4-tag-inventory-results.md` §4.1).
Слово «вроде» здесь важно — это умеренная, не категоричная уверенность. Подтверждение
относится к группе A целиком; про группу B (`arousal`, `confusion`, `helplessness`,
`longing`) и про два тега группы C (`anger`, `enthusiasm`) владелец ничего не говорил —
считайте их непроверенными на слух.

**`<|style:whispering|>` не даёт шёпота.** Энергия падает всего на ~3 дБ относительно
нейтральной речи (а не резко, как при настоящем шёпоте), а медиана F0 совпадает с
нейтральной до одного знака после запятой — то есть основной тон никуда не пропадает, а
именно это отличает акустический шёпот от просто тихой озвученной речи. Тег измеримо
отличим от нейтрали (более тихо, другая структура пауз), но не заменяет реальное
шёпотное произношение. Подтверждено дважды независимо — метриками в двух разных прогонах
(`m4-sentiment-results.md` §6b, `m4-tag-inventory-results.md` §4). Не используйте
`<|style:whispering|>` в сценарии в расчёте на слышимый шёпот.

**Темп (`prosody:speed_*`) — на управление им полагаться нельзя.** Первое измерение
(`m4-sentiment-results.md`) поймало у `speed_slow` чистый эффект (-16% темпа); второе, на
другом тексте (`m4-tag-inventory-results.md`), почти не увидело эффекта ни у одного из
четырёх тегов `speed_*`, причём `speed_very_fast`/`speed_very_slow` иногда двигались в
обратную сторону от названия. Это не противоречие, а разрешённая нестыковка: по вердикту
владельца, **«медленный голос не всегда сильно медленнее»** — эффект у тега реальный, но
слабый и непостоянный от прогона к прогону, не «пустышка», но и не надёжный инструмент.
Если сценарию нужна неспешность, закладывайте её пунктуацией и паузами (раздел 5), а не
одним лишь тегом темпа.

**Пауза (`prosody:pause`/`long_pause`) — рабочий, но одноразовый эффект.** Оба тега дают
измеримую паузу; ставятся один раз в конкретную позицию текста, не переоткрываются как
состояние (см. `INLINE_ONE_SHOT_PROSODY` в `src/audiobook.py` и раздел 3 ниже).

**Девять `sfx`-тегов существуют в словаре модели, но ни разу не проверялись даже
метриками** — не используйте их в сценарии, не убедившись отдельно, что они вообще что-то
делают.

Про остальные теги, не упомянутые выше (все `prosody:pitch_*`, `prosody:expressive_*`,
`style:shouting`, `style:singing` и т.д.), есть только метрики группы A/B/C, но не
подтверждение на слух — обращайтесь с ними как с кандидатами, а не готовым инструментом.

### 5a.1 Итог для автора сценария: чем реально пользоваться, а чем нет

| Инструмент | Статус | Источник |
| :--- | :--- | :--- |
| Эмоции (`emotion:*`, группа A, 15 тегов) | **Основной рабочий инструмент** — подтверждены метриками и на слух | `m4-tag-inventory-results.md` §4, §4.1; `m4-sentiment-results.md` §6 |
| Ударения через апостроф (`за'мок`) | **Обязательны** для омографов — без них модель угадывает сама и не всегда верно | `m4-tag-inventory-results.md` §3.6, §3.8; раздел 5b ниже |
| Паузы (`prosody:pause`/`long_pause`) | Рабочие, но одноразовые — ставятся в конкретную позицию, не переоткрываются | `src/audiobook.py` `INLINE_ONE_SHOT_PROSODY`; PROMPTING.md |
| Управление темпом (`prosody:speed_*`) | **Ненадёжно** — эффект слабый и непостоянный; неспешность закладывайте пунктуацией/паузами | `m4-tag-inventory-results.md` §4.1a |
| `style:whispering` | Не даёт шёпота, только тише | `m4-sentiment-results.md` §6b; `m4-tag-inventory-results.md` §4 |
| `sfx`-теги (9 штук) | Существуют, но не проверены даже метриками — не полагайтесь | `m4-tag-inventory-results.md` |
| Эмоции групп B/C, `pitch_*`, `expressive_*`, `style:shouting`/`singing` | Есть только объективная метрика, нет подтверждения на слух | `m4-tag-inventory-results.md` §4 |

## 5b. Расстановка ударений — обязательна для русского текста

### Почему это не опционально

На нескольких проверенных омографах (`замок`/`за́мок`, `стоит`/`сто́ит`, `атлас`/`а́тлас`)
владелец подтвердил на слух: **если ударение в слове не проставлено явно, модель выбирает
его сама, произвольно, и не всегда правильно.** Прямая цитата (2026-08-25):

> «там где нет ударений, он выбирает случайное ударение
> ...
> причем видно что если ударение непроставлено, то он выбирает свое, и не всегда правильное»

Это значит, что для книги с омографами (а в русском языке они не редкость — «за́мок» vs.
«замо́к», «а́тлас» vs. «атла́с», «стои́т» vs. «сто́ит» и десятки других пар) одинаковый
непомеченный текст может в одном прогоне озвучиться правильно, а в другом — с неверным
ударением. Это дефект корректности, а не только качества: **расстановка ударений для
русской книги на этом бэкенде необходима, а не желательна.**

### Какая нотация работает, а какая нет

Проверено (`docs/research/audiobook/m4-tag-inventory-results.md` §3): 6 нотаций ударения
на 3 парах омографов, проверка (a) объективная — распознаётся ли текст обратно без
искажений, и (b) на слух владельцем.

| Нотация | Пример | Вердикт |
| :--- | :--- | :--- |
| **Апостроф после ударной гласной** | `за'мок` | **Работает.** Ни разу не озвучен буквально, даёт правильное ударение по подтверждению на слух. Единственная нотация, рекомендованная к использованию. |
| Удвоение гласной | `заамок` | **Не ударение.** Проговаривается как удвоенная буква, удлиняя звук — эффект длительности, а не ударения. |
| Заглавная буква | `зАмок` | Ненадёжна — иногда даёт ударение, иногда только смысловое (логическое) выделение слова целиком, не сдвиг ударения на слог. |
| `+` перед ударной гласной | `з+амок` | Не использовать — иногда произносится вслух (как буква «п» либо, в аналогичном сбое на другом бэкенде, как слово «плюс»). |
| Комбинирующее ударение U+0301 | `за́мок` | Не проверено на слух отдельно от прочих — не рекомендуется до отдельной проверки. |
| Без пометки | `замок` | Модель выбирает ударение сама и не всегда верно — не считайте это безопасным вариантом по умолчанию. |

**Используйте апостроф после ударной гласной** (`за'мок`, `сто'ит`) как единственную
проверенную нотацию для мест, где значение слова зависит от ударения.

### Ловушка: апостроф в именах собственных

Апостроф в русской транслитерации законно встречается в именах и заимствованиях —
«д'Артаньян», «О'Генри». Если трактовать любой апостроф как ударение, эти имена сломаются
(и такое поведение вообще не то, что нужно для имени). `src/audiobook.py` разделяет два
случая эвристикой (`is_stress_apostrophe`): апостроф считается ударением, **только если**
он стоит строго внутри одного строчного слова — сразу после строчной русской гласной и
сразу перед строчной русской буквой, продолжающей то же слово. Оба примера имён не
проходят это правило: в «д'Артаньян» перед апострофом согласная, а после — заглавная
буква; в «О'Генри» перед апострофом гласная, но после — заглавная буква. Это компромисс,
а не доказанное лингвистическое правило: гипотетическое имя, написанное строчными буквами
по обе стороны от апострофа (в собранных примерах такого не встретилось), эта эвристика
всё равно ошибочно примет за ударение.

На практике эта эвристика используется только для информационных счётчиков в манифесте
(см. ниже) — сам движок ничего не делает с апострофом, кроме того что аккуратно проносит
его через разбиение на предложения, нарезку на чанки и валидацию тегов, ничего не меняя.
Финальную интерпретацию апострофа как ударения делает сама модель Higgs при генерации.

### Как понять, что текст уже размечен ударениями

Автору сценария нужно знать, обработан ли конкретный текст — иначе легко расставить
ударения дважды или, наоборот, забыть про уже готовую главу. `build_manifest` в
`src/audiobook.py` автоматически (без отдельного флага, который легко забыть передать)
считает в тексте главы количество апострофов, похожих на ударение
(`stress_marks_detected`), и апострофов, не похожих на ударение — вероятных имён
(`ambiguous_apostrophes_detected`) — и записывает оба числа в `manifest.json`. Проверьте
эти поля перед тем, как начинать вручную расставлять ударения в уже обработанной главе,
или чтобы убедиться, что необработанная глава действительно не тронута (`0` в обоих
полях для текста без единого апострофа).

### Пример на омографах

Без ударения одна и та же строка неоднозначна:

```
На холме стоит старинный замок.
```

Здесь «замок» может значить «за́мок» (крепость) или «замо́к» (устройство запирания) — по
смыслу предложения понятно человеку, но не факт, что модель выберет то же самое. С
ударением неоднозначности нет:

```
На холме стоит старинный за'мок.
```

### Дальнейшая работа: как расставить ударения по всей книге (открытый вопрос)

Вручную проставить ударения апострофом в каждом омографе целой книги нереально — их
десятки на главу в обычном тексте, и пропуск одного не диагностируется автоматически (см.
выше про `stress_marks_detected`/`ambiguous_apostrophes_detected` — эти счётчики видят
факт наличия апострофов, но не то, правильно ли расставлено конкретное ударение). Ниже —
варианты автоматизации без выбора между ними; решение остаётся за владельцем проекта.

| Вариант | Идея | Цена |
| :--- | :--- | :--- |
| Словарь омографов | Список известных неоднозначных слов с правилами выбора ударения по контексту (часть речи, падеж, соседние слова) | Нужно собрать/найти словарь омографов для русского; ручные правила не покрывают весь язык, только частотные пары |
| Морфологический анализатор (напр. pymorphy2/pymorphy3, Stanza) | Автоматический разбор части речи и грамматической формы слова, которые часто однозначно определяют ударение | Дополнительная тяжёлая зависимость (противоречит правилу проекта не тянуть в конвейер лишние библиотеки без проверки); не решает случаи, где омограф неоднозначен даже морфологически (напр. «за́мок»/«замо́к» — оба существительные, различаются только смыслом) |
| Отдельная модель ударения (napr. RUAccent и подобные акцентуаторы) | Специализированная ML-модель, предсказывающая ударение по всему предложению с учётом контекста | Ещё одна модель в конвейере — лишний вес, время инференса на каждую главу, риск собственных ошибок, которые проект не сможет отличить от исходной проблемы без нового прослушивания |

Ни один из вариантов не реализован в рамках этой работы. Если один из них будет выбран,
его вывод — обычный текст с уже расставленными апострофами — подать в существующий
конвейер без изменений: расстановка ударений и генерация речи целенаправленно разделены.

## 6. Экспорт в финальные форматы (MP3 / M4B)

Для удобного прослушивания на телефонах и в плеерах готовый WAV легко конвертируется через `ffmpeg`:

```bash
# Конвертация в MP3 (высокое качество 192 kbps):
ffmpeg -i output/audiobook/chapter_01.wav -codec:a libmp3lame -b:a 192k output/audiobook/chapter_01.mp3

# Конвертация всей книги в аудиокнигу M4B с закладками:
ffmpeg -i output/audiobook/chapter_01.wav -c:a aac -b:a 128k output/audiobook/audiobook.m4b
```
